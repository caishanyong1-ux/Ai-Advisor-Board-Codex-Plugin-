# Change members during a meeting

A user request or chairman recommendation can trigger reconsideration. A new ranking is evidence for a proposal, never permission to replace members automatically.

1. Call `board_pause` for the current job. `pausing` stops new dispatch while accepted requests finish; they may still incur charges. Poll status with sensible spacing until `paused`. Preserve completed and partial statements. Cancellation is a separate user intent.
2. Inspect all saved statements, failures and accounted costs. Identify the new assignment, why the current lineup is insufficient, which members stay/change and what the incoming members need. Apply grilling only to consequential unresolved choices.
3. Follow [models-and-providers.md](models-and-providers.md) to refresh rankings **after the pause**. Record a new `selection_id`, compare task fit and cost, and offer concrete lineup/workflow options using [selection-message.md](selection-message.md). The user approves both dimensions.
4. Call `board_reconfigure` with scope, current `job_id`, current `conversation_id`, new full `plan`, change `reason`, and an explicit `history_summary` only if needed. The new budget is additional to already accounted costs; use the old remaining amount when sufficient. Keep old spend, old remaining budget, new requested budget, and combined accounted cost plus new budget in Details and the human approval page; the initial chat shows only the recommended lineup. Uncertain prior calls are still accounted for.
5. The old job becomes `reconfiguration_pending`; the child is `awaiting_approval`. The human submits the new local approval page. On approval, the old revision becomes `superseded` and the new members receive the approved historical packet. Their new statements are independent contributions; historical statements are not new votes. This is a new lineup revision within the same board project, not project closure.
6. If the user rejects the proposed revision, cancel the pending child. This releases the old revision to `paused`. Use `board_resume` and its separate human confirmation to continue the unchanged old lineup. Fresh revisions can instead be prepared with refreshed research. A superseded revision stays historical.

A paused meeting survives worker restarts. Already-successful steps are reused when resuming an unchanged revision; changed assignments in a new revision produce new member calls. Saved answers are retained as evidence rather than silently relabelled as answers from the replacement lineup. Only the human can close the board project.
