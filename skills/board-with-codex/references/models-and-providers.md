# Refresh recommendations and connect providers

Perform this process before each new paid agenda and after pausing a meeting for a membership change. It is automatic work by the Codex chairman within this skill, not an unattended ranking scraper or a promise of background updates.

1. Carry the human-selected `thinking_level` from the grilling round. Inspect `board_models`, `board_connections`, and `board_model_policy`; read the **complete available `inventory`**, regardless of detail pagination. Consider every locally eligible entry within existing access and compare task-relevant capability combinations. Different makers are useful candidates, not a required quota; different models from one maker can complement. The chosen board needs Codex plus at least four distinct external models. `considered_models` must contain every inventory ID whose `selection_allowed` is true; consideration is not inference testing or individual benchmarking. Public preserves Claude; personal excludes it and reuses available direct xAI. Own-API presets are setup choices, not connected models. Never read credentials into chat/tool arguments.
2. Browse **at least two independent primary benchmark sources** relevant to this task. Useful starting points: [Artificial Analysis](https://artificialanalysis.ai/leaderboards/models), [Arena](https://arena.ai/leaderboard), [LiveBench](https://livebench.ai/), [SWE-bench](https://www.swebench.com/). Arena and LMArena are one source. Check the current release and evaluation date; old repository branches may lag a deployed leaderboard. For LiveBench, discover its current release first, then inspect that release's table/categories/notes. Never hardcode a dated release as latest.
3. Match exact model version, reasoning setting, harness, tools and modality. Preference votes, coding-agent scores and reasoning scores measure different outcomes: explain their relevance instead of adding scores across benchmarks. Preliminary scores, uncertainty, sample size and missing independent evidence belong in limitations. If access fails, record the attempted source with `available:false`; explain the fallback and lower confidence. Screenshots are clues, not current verification.
4. Check official exact API IDs, settings, context, retirement, account access and full tariffs. For each proposed model compare **its already connected usable routes**, matching version, reasoning, token accounting, context tier, caching assumptions and billing currency. An open model's Vertex markup can favor another already connected route. Unconnected APIs stay outside this selection; they are considered only in the separate user-requested setup flow. Record unavailable prices/access honestly, not guessed savings. The highest level does not sacrifice capability to save cost; balanced and economy apply their chosen tradeoffs. All levels retain four external models. Price pages can retain retired entries; dated retirement notices take precedence. Listing is not entitlement. Price quotes last at most seven days; cap around changes. After price/setup changes refresh `board_models` for its final fingerprint.
5. Record `board_recommend` with scope, task type, criteria, **thinking_level**, **difficulty_assessment**, evidence, candidates, final catalog fingerprint, all considered IDs, and **route_comparisons**. `candidates` covers every considered eligible model, not only the shortlist: exact model, supported effort, task fit, value reason (including non-selection), evidence indices, limitations, recommend. Recommend at least four distinct models with documented complementary capabilities. Evidence uses HTTPS URL, ISO checked_at, kind (benchmark/availability/pricing/capability), finding and optional available. A route comparison has model, comparison and evidence_indices; describe current access, verified tariffs and meaningful differences. Save comparisons for every model that might appear in a proposed option, including a user-selected external chairman. Records retain reasoning internally for on-demand disclosure; do not dump it into the default chat. Missing assessments/routes block new research/proposals. A complete project-scoped selection ID lasts 24 hours.
6. Use [selection-message.md](selection-message.md) for the lineup-only choice with **Use / Adjust / Details**. Keep costs, reasons, workflow, settings and other candidates in the saved details. Only after **Details** or an explicit costs/reasons request, call `board_selection_details` and give one complete response covering every considered model, capability complementarity, why selected or not, route comparisons and limitations. Do not invent historical reasons absent from a legacy record; refresh that research. Include selection ID and matching thinking level in prepare/followup/reconfigure. A changed ranking or a request to view reasons never changes an approved lineup or starts a model call.

## Existing access and user-requested additions

Default `board_models` includes enabled configured routes with usable adapters and no known access block; edition exclusions and retired entries are absent. A stale/missing tariff stays visible for a price refresh but cannot enter `board_recommend` until priced. Configuration is not proof of successful inference or partner entitlement. Check available read-only account evidence; omit known gated/denied models. Do not send a paid probe during selection.

A formal board still needs four distinct external models. If the current available pool cannot meet that requirement, report the shortage and leave the meeting pending. Do not initiate API setup or reduce the minimum. When the human explicitly asks to add/manage API or model access, follow [api-connections.md](api-connections.md). That separate flow preserves provider suggestions and private credential entry.

Retired Vertex routes do not disable separately configured original-provider APIs. Verify each route's lifecycle independently. New models on an existing connected route may be registered after verifying current official protocol, prices and account requirements; registration does not establish entitlement.

## Cost semantics

Gemini and Claude adapters include thinking in output accounting. Legacy Claude 4.5 uses explicit token budgets; low/medium/high mean 1024/4096/8192 thinking tokens and require a larger total output cap. Modern Claude uses adaptive thinking and supported effort levels. The approval page displays this difference and Fable's additional data-sharing conditions.

**Grok has no verified hard total reasoning cap.** Its output parameter limits visible text; the initial estimate assumes 128K reasoning tokens, which is an estimate, not a limit. These calls run sequentially after bounded calls and reserve the whole remaining dispatch budget. The human must separately acknowledge variable cost on the approval page. xAI's returned `cost_in_usd_ticks / 10^10` reconciles cost when present; otherwise retain the reservation and stop further paid steps when budget is unavailable. Actual charges may exceed the dispatch budget. Use xAI account controls for provider-side limits; do not claim an app token cap guarantees the bill. User-configured Grok endpoints receive the same warning.

Input snapshots use a conservative UTF-8 byte bound plus framing; model-specific context/input limits and output parameters are enforced. Timeouts/unknown calls keep reservations. New prices or credentials do not silently redirect approved requests. Local cost history is useful for comparable tasks, never a universal quality-per-dollar score.
